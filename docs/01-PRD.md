# TripPick — 제품 요구사항 정의서 (PRD)

> 개인용 여행 정보 수집·알림 서비스. 조건을 등록해두면 항공권·숙소 가격을 주기적으로
> 추적하다가 기준을 만족할 때 슬랙으로 알려준다.

---

## 1. 한 줄 정의

**"내가 가고 싶은 여행의 조건을 등록해두면, 값이 떨어졌을 때 나에게 먼저 알려주는 개인 비서."**

## 2. 사용자 / 사용 맥락

- 사용자: 본인 1명 (single-tenant). 인증은 MVP에서 단일 API 토큰으로 처리하고,
  멀티유저 확장 여지만 스키마에 남겨둔다.
- 사용 맥락: PC에 docker-compose로 상시 실행 → 슬랙으로 푸시를 받는다.
  가격 히스토리나 상세 비교가 필요할 때만 웹 대시보드에 접속한다.
- **웹은 "관리·분석 화면"이고, 슬랙이 "주 소비 채널"이다.** 이 우선순위를 UI 설계에 반영한다.

## 3. 핵심 문제

1. 항공권/숙소 가격은 하루에도 수 차례 변한다. 사람이 계속 볼 수 없다.
2. "언제든 좋으니 오사카 30만원 밑으로 뜨면 알려줘" 같은 **유연한 조건**을 지원하는 서비스가 없다.
   (대부분은 특정 날짜 고정 알림만 지원)
3. 가격이 싼 건지 판단할 기준(과거 이력)이 없다. → **내가 모은 데이터가 곧 기준선이 된다.**

## 4. 범위

### Phase 1 — MVP (이 문서의 구현 대상)

| # | 기능 | 설명 |
|---|---|---|
| F1 | 감시 조건 등록 (Watch) | 항공/숙소 조건을 등록·수정·삭제·일시중지 |
| F2 | 주기적 가격 수집 | 스케줄러가 Watch별 주기로 소스를 조회해 스냅샷 저장 |
| F3 | 알림 규칙 평가 | 목표가 도달 / N% 급락 / 역대 최저가 / 신규 최저 등 규칙 판정 |
| F4 | 슬랙 알림 | Block Kit 메시지로 발송. 중복 억제(dedup)와 쿨다운 포함 |
| F5 | 웹 대시보드 | 감시 목록·가격 히스토리 차트·오퍼 목록·알림함·설정 |
| F6 | 소스 어댑터 레이어 | 소스별 구현을 공통 인터페이스 뒤로 숨김 (교체·추가 비용 최소화) |

### Phase 2 — 취향 기반 추천 (로드맵)

- 온보딩 설문 → 취향 프로필(벡터) 생성
- 공공데이터 관광정보(TourAPI)에 취향 스코어링 → 목적지·장소 추천
- "너 취향인 곳인데 지금 항공권 싸다" 형태의 결합 알림

### Phase 3 — 여행 루트

- 지도 기반 일정 편집, 이동시간 고려한 동선 최적화
- 날씨·축제·휴무일 데이터 결합
- 루트 → 필요한 항공/숙소를 역으로 Watch로 등록

### 명시적 비범위 (Non-goals)

- 실제 예약/결제 기능 (외부 링크로 넘긴다)
- 다중 사용자 회원가입/과금
- 봇 차단 우회, 캡차 우회, 로그인 세션 탈취형 수집 — **하지 않는다** (`03-DATA-SOURCES.md` 참조)

## 5. 사용자 시나리오

### S1. 유연한 항공권 감시

> "10~12월 중 아무 주말이나, 인천 → 후쿠오카 왕복 2~3박, 25만원 이하면 알려줘"

1. 웹에서 Watch 등록: `type=flight`, `ICN→FUK`, 기간 `2026-10-01 ~ 2026-12-31`,
   `trip_length 2~3박`, `target_price 250000`, `주말 선호`
2. 워커가 6시간마다 소스 조회 → 날짜 조합별 최저가 스냅샷 저장
3. 11/14~11/16 조합이 238,000원 → 규칙 `threshold` 통과
4. 슬랙 알림: 가격, 날짜, 항공사, 직전가 대비 변동, 예약 링크, 90일 내 최저 여부

### S2. 숙소 감시

> "12/24~12/26 서울 4성급 이상, 2인, 15만원 이하"

동일 흐름. 소스만 숙소 어댑터로 바뀐다.

### S3. 급락 감지 (목표가 없음)

> "목표가는 모르겠고, 평소보다 20% 이상 떨어지면 알려줘"

규칙 `drop_pct=20`, 기준선은 최근 14일 중앙값.

## 6. 성공 기준 (Definition of Done, Phase 1)

- [ ] Watch를 등록하면 재시작 후에도 스케줄이 유지된다
- [ ] 소스 1개가 장애여도 다른 소스로 수집이 계속되고, 실패는 `source_health`에 기록된다
- [ ] 동일 조건에 대해 같은 알림이 쿨다운 내에 두 번 오지 않는다
- [ ] 가격 히스토리 차트가 최소 30일치 데이터를 렌더링한다
- [ ] `docker compose up` 한 번으로 전체 스택이 뜬다
- [ ] 슬랙 → 텔레그램 전환이 **환경변수 한 줄 변경 + 렌더러 파일 1개 추가**로 끝난다
- [ ] 백엔드 핵심 로직(규칙 평가, 어댑터 정규화) 테스트 커버리지 80% 이상

## 7. 제약 및 원칙

| 항목 | 결정 | 이유 |
|---|---|---|
| 실행 환경 | 지금은 로컬 docker-compose, 이후 클라우드 | 클라우드 이전 시 재작성이 없도록 **처음부터 컨테이너 + Postgres**. SQLite 금지 |
| 상태 저장 | 전부 Postgres. 파일 시스템 상태 없음 | 클라우드 이전 시 볼륨 종속 제거 |
| 시크릿 | 모두 `.env` → `app/config.py`(pydantic-settings) 경유 | 코드에 키 하드코딩 금지 |
| 시간대 | DB 저장은 전부 UTC, 표시 시점에 KST 변환 | 스케줄 버그의 가장 흔한 원인 차단 |
| 통화 | 저장은 KRW 정수(원 단위). 소스가 다른 통화면 수집 시점 환율로 환산 후 원본도 함께 보관 | 비교 가능성 |
| 수집 예의 | 요청 간격·동시성 제한·캐싱·robots.txt 준수 | `03-DATA-SOURCES.md` |
